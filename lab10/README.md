# Лабораторная работа №10

## Описание задания

В данной лабораторной работе необходимо реализовать базовые механизмы защиты данных на языке Go: хэширование, симметричное и асимметричное шифрование, электронную подпись, защищённый канал TLS, аутентификацию REST API по токенам (JWT), а также защиту от CSRF и управление сессиями.

Все задания расположены в папке `lab10`, каждое в своей подпапке `taskN` (N — номер задания от 1 до 6).

## Структура проекта

```
lab10/
├── task1/main.go               — хэширование данных (MD5, SHA-256, SHA-512)
├── task2/main.go               — симметричное шифрование AES (GCM)
├── task3/main.go               — асимметричное шифрование и цифровая подпись RSA
├── task4/
│   ├── main.go                 — генерация сертификатов (CA, сервер, клиент)
│   ├── server/server.go        — TLS-сервер с взаимной аутентификацией
│   ├── client/main.go          — TLS-клиент с проверкой сертификата сервера
│   └── certs/                  — созданные сертификаты и ключи
├── task5/
│   ├── main.go                 — REST API с JWT и ролевым доступом
│   └── requests.http           — примеры запросов для проверки
├── task6/
│   ├── main.go                 — REST API с сессиями и защитой от CSRF
│   └── requests.http           — примеры запросов для проверки
└── README.md
```

Требуется Go 1.22 или новее (используется `http.ServeMux` с шаблонами путей и `r.PathValue`). Для задания 5 нужна библиотека `github.com/golang-jwt/jwt/v5`.

## Задание 1. Хэширование данных

**Файл:** `task1/main.go`

Утилита вычисляет хэш введённой строки одним из алгоритмов: MD5, SHA-256 или SHA-512. Также реализована проверка целостности: пользователь вводит строку и её хэш, программа определяет алгоритм по длине хэша (32/64/128 символов) и подтверждает или опровергает соответствие.

```
Хэширование
1. Вычислить хэш строки
2. Проверить целостность
0. Выход
Выберите пункт: 1
Алгоритмы: 1 - MD5, 2 - SHA-256, 3 - SHA-512
Выберите: 2
Введите строку: привет
SHA-256: 5d5c4d2b7b8f1f0e...
```

Запуск: `go run ./lab10/task1`

## Задание 2. Симметричное шифрование AES

**Файл:** `task2/main.go`

Строка шифруется алгоритмом AES в режиме GCM. Ключ любой длины приводится к 32 байтам через SHA-256. Случайный nonce генерируется при каждом шифровании и сохраняется вместе с шифротекстом; результат выводится в hex-виде. Расшифровать строку можно только тем же ключом — при неверном ключе или изменённых данных выводится ошибка.

```
Шифрование AES
1. Зашифровать строку
2. Расшифровать строку
0. Выход
Выберите пункт: 1
Введите строку: секрет
Введите ключ: qwerty
Зашифрованная строка: 8f3a...c1
```

Запуск: `go run ./lab10/task2`

## Задание 3. Асимметричное шифрование и цифровая подпись

**Файл:** `task3/main.go`

Программа создаёт пару ключей RSA (2048 бит) и сохраняет их в файлы `private.pem` и `public.pem`. Сообщение подписывается закрытым ключом (RSA + SHA-256, PKCS#1 v1.5), подпись проверяется открытым ключом. В пункте 4 приведён пример передачи сообщений между двумя сторонами: подпись верна для исходного сообщения, неверна при подмене текста и неверна при подделке подписи чужим ключом.

2. Подписать сообщение
3. Проверить подпись
4. Пример: передача сообщений между двумя сторонами
0. Выход
```

Запуск: `go run ./lab10/task3`

## Задание 4. Защищённый канал передачи данных (TLS)

**Файлы:** `task4/main.go`, `task4/server/server.go`, `task4/client/main.go`

1. `main.go` создаёт в папке `certs` центр сертификации (`ca.crt`, `ca.key`), сертификат сервера (`server.crt`, `server.key`, DNS-имя `localhost`) и сертификат клиента (`client.crt`, `client.key`). Все сертификаты подписаны CA.
2. `server/server.go` — TLS-сервер на порту 8080, который требует и проверяет клиентский сертификат (`tls.RequireAndVerifyClientCert`), то есть реализована взаимная аутентификация. Сервер выводит имя клиента из сертификата, принимает сообщение и отправляет ответ.
3. `client/main.go` — TLS-клиент, который проверяет сертификат сервера по `ca.crt` и предъявляет свой сертификат. При запуске с аргументом `nocert` клиент не отправляет сертификат, и сервер отклоняет соединение.

**Запуск (по порядку, из папки `lab10/task4`):**

```
go run .                          # 1. создать сертификаты в certs/
go run ./server                   # 2. запустить сервер (терминал 1)
go run ./client                   # 3. клиент с сертификатом (терминал 2)
go run ./client nocert            # 4. клиент без сертификата — отказ
```

Пример работы:

```
Соединение защищено (TLS 1.3). Сертификат сервера проверен: server
Введите сообщение:
привет
Отправлено: привет
Ответ сервера: Сообщение получено: привет
```

## Задание 5. Защита REST API (JWT и роли)

**Файлы:** `task5/main.go`, `task5/requests.http`

REST API для работы с пользователями. Вход через `POST /login` проверяет логин и пароль и выдаёт JWT (HS256, срок действия 1 час) с полями `username` и `role`. Middleware `protect` проверяет токен из заголовка `Authorization: Bearer <токен>` и роль пользователя:

| Метод и путь | Роль |
|---|---|
| `POST /login` | без токена |
| `GET /users`, `GET /users/{id}` | user, admin |
| `POST /users`, `PUT /users/{id}`, `DELETE /users/{id}` | только admin |

Учётные записи: `admin / admin123` (роль admin), `user / user123` (роль user).

Ответы: 200/201/204 при успехе, 401 при отсутствии или неверном токене, 403 при недостатке прав, 400 при неверных данных, 404 если пользователь не найден.

Запуск: `go run ./lab10/task5`, затем выполнить запросы из `requests.http` (расширение REST Client для VS Code).

Пример работы:

```
Сервер запущен: http://localhost:8080
```

Запросы из `requests.http` проверяют: вход admin и user, неверный пароль (401), запрос без токена и с мусорным токеном (401), чтение списка и одного пользователя ролью user (200), попытку добавить и удалить пользователя ролью user (403), полный CRUD ролью admin (201/200/204).

## Задание 6. Защита от CSRF и управление сессиями

**Файлы:** `task6/main.go`, `task6/requests.http`

API из задания 5 переведено на сессии:

- при входе сервер создаёт сессию (случайный идентификатор, срок жизни 30 минут) и кладёт её в cookie `session_id` с флагами `HttpOnly` и `SameSite=Strict`;
- вместе с сессией выдаётся CSRF-токен, который клиент присылает в заголовке `X-CSRF-Token`;
- middleware `protect` проверяет наличие действующей сессии (иначе 401) и для всех методов, кроме GET, — совпадение CSRF-токена (иначе 403);
- `POST /logout` уничтожает сессию, `GET /sessions` возвращает информацию о текущей сессии.

Так поддельный запрос с чужого сайта не пройдёт: cookie отправится браузером, но CSRF-токена у злоумышленника нет.

Запуск: `go run ./lab10/task6`, затем выполнить запросы из `requests.http` сверху вниз (REST Client сам сохраняет cookie, как браузер).

Пример работы:

```
Сервер запущен: http://localhost:8080
```

Запросы из `requests.http` проверяют: запрос без входа (401), вход и получение csrf_token (200), информацию о сессии и чтение списка (200), поддельный POST без CSRF-токена (403), запрос с неверным токеном (403), настоящий POST с токеном (201), обновление (200), удаление без токена (403) и с токеном (204), выход (204) и отказ после выхода (401).
